    Chapter 17: Transactions 事务

    1. Transaction Concept

    DBMS 需要处理两个核心问题:

    • 多用户或多程序的并发执行
    • 各类故障
    • 硬件故障
    • 系统崩溃
    • 事务内部错误

    Transaction 事务:

    访问并可能更新多个数据项的一段程序执行单元

    通常一个事务由若干 SQL 语句组成, 并以:

    • commit
    • rollback

    结束

    事务需要满足:

    • 事务开始时看到的数据库应该是一致的
    • 事务执行过程中数据库可以暂时不一致
    • 事务提交后数据库必须重新一致

    1.1 ACID Properties

    为了保持数据库的完整性, DBMS 需要保证事务的 ACID 性质

    Atomicity 原子性

    • 事务的所有操作要么全部反映到数据库中
    • 要么全部不反映

    由 transaction-management 和 recovery-management 负责

    Consistency 一致性

    • 事务在隔离执行时, 应保持数据库一致性

    主要由 application programmer 负责保证事务逻辑正确

    Isolation 隔离性

    • 多个事务并发执行时, 每个事务都不应感知到其他并发事务的中间结果
    • 一个事务的中间状态必须对其他事务隐藏

    由 concurrency-control component 负责

    Durability 持久性

    • 事务成功完成后, 即使系统发生故障, 它对数据库的修改也必须保留

    由 recovery-management component 负责

    1.2 Fund Transfer Example

    从账户 A 转 50 到账户 B:

    read(A)
A := A - 50
write(A)
read(B)
B := B + 50
write(B)
commit

    原子性:

    • 若事务在写 A 后、写 B 前失败
    • 系统必须保证 A 的修改不会单独留在数据库中

    一致性:

    • 执行前后 $A+B$ 的总和不变

    持久性:

    • 一旦用户收到转账成功通知, 即使之后系统崩溃, 更新也必须保留

    隔离性:

    • 若另一个事务在写 A 后、写 B 前读取数据库
    • 它会看到 $A+B$ 减少的不一致状态

    串行执行可以简单保证隔离性, 但并发执行有更高性能, 因此需要并发控制

    1.3 Transaction Definition in SQL

    在 SQL 中:

    • 事务隐式开始
    • 当前事务可以通过以下语句结束:
    commit work;

    提交当前事务并开始新事务

    rollback work;

    回滚当前事务

    2. Transaction State 事务状态

    事务可能处于以下状态: - Active - 初始状态 - 事务正在执行 - Partially committed - 最后一条语句已经执行完 - 但结果可能还在内存 buffer 中 - Failed - 发现无法继续正常执行 - Committed - 事务成功完成 - Aborted - 事务已经回滚 - 数据库恢复到事务开始前状态

    事务 aborted 后有两种选择:

    • restart transaction
    • 适用于不是事务内部逻辑错误导致的失败
    • kill transaction

    3. Implementation of Atomicity and Durability

    原子性和持久性由 recovery-management component 支持

    3.1 Shadow-Database Scheme 影子数据库

    shadow-database scheme 是一种简单但低效的方法

    核心思想:

    • 有一个指针 db_pointer 始终指向当前一致的数据库副本
    • 所有更新都在新创建的数据库副本上完成
    • 原始副本不被修改, 称为 shadow copy 影子拷贝

    若事务 abort:

    • 直接删除新副本
    • db_pointer 仍指向原 shadow copy

    若事务 commit:

    1. 将新副本中所有内存页 flush 到磁盘
    2. 原子地修改 db_pointer, 使其指向新副本
    3. 删除旧副本

    要求:

    • db_pointer 的更新必须是原子的
    • 通常存放在单个 disk sector 中
    • 没有并发事务
    • 假设磁盘本身不会损坏

    缺点:

    • 对大型数据库极其低效
    • 单个事务也需要复制整个数据库

    该思想适合文本编辑器, 但不适合大型 DBMS; 后续恢复系统会使用更好的日志方法

    4. Concurrent Executions 并发执行

    DBMS 允许多个事务并发执行

    优点:

    • 提高处理器和磁盘利用率
    • 一个事务使用 CPU 时, 另一个事务可以读写磁盘
    • 提高 transaction throughput 吞吐量
    • 降低平均响应时间
    • 短事务不用等待长事务全部完成

    问题:

    • 即使每个事务单独执行都是正确的
    • 并发交错执行仍可能破坏一致性

    因此需要:

    concurrency control schemes 并发控制机制

    目标:

    • 实现 isolation
    • 控制并发事务之间的相互影响
    • 防止并发执行破坏数据库一致性

    4.1 Schedules 调度

    schedule 调度:

    表示并发事务中各条指令按时间执行顺序排列的序列

    这里虽然交换顺序后 A B 结果不一样, 但是不破坏一致性要求

    一个 schedule 必须:

    • 包含所有事务的所有指令
    • 保持每个事务内部指令的原有顺序

    serial schedule 串行调度: （图片文件缺失：Pasted image 20260626135826.png） - 一个事务完全执行完后, 下一个事务才开始 - 若有 $n$ 个事务, 可能有 $n!$ 种串行调度

    串行调度一定能保持一致性, 但并发度低

    concurrent schedule 并发调度: - 多个事务的指令交错执行 - 可能保持一致性, 也可能破坏一致性

    5. Serializability 可串行化

    显然, 串行执行一组事务可以保持数据库一致性

    问题是:

    一个并发 schedule 是否等价于某个 serial schedule?

    定义:

    serializable schedule 可串行化调度:

    Definition: 如果一个 schedule 等价于某个 serial schedule, 则称它是 serializable

    serializable schedule 是正确的并发调度

    常见等价概念:

    • conflict serializability 冲突可串行化
    • view serializability 视图可串行化

    为讨论方便, 下文只考虑:

    • read(Q)
    • write(Q)

    5.1 Conflict Serializability

    两个不同事务 $T_i$, $T_j$ 的指令 $l_i$, $l_j$ 冲突当且仅当:

    • 它们访问同一个数据项 $Q$
    • 且至少一个操作是 write(Q)

    四种情况:

    • read(Q) 与 read(Q) 不冲突
    • read(Q) 与 write(Q) 冲突
    • write(Q) 与 read(Q) 冲突
    • write(Q) 与 write(Q) 冲突

    冲突操作的执行顺序不能交换; 非冲突操作可以交换

    conflict equivalent 冲突等价:

    若 schedule $S$ 可以通过一系列非冲突指令的交换变成 $S'$, 则 $S$ 与 $S'$ 冲突等价

    conflict serializable 冲突可串行化:

    若一个并发 schedule 与某个 serial schedule 冲突等价, 则它是 conflict serializable

    6. Recoverability 可恢复性

    并发事务中, 若一个事务读取了另一个尚未提交事务写入的数据, 就可能产生恢复问题

    6.1 Recoverable Schedule

    recoverable schedule 可恢复调度:

    若事务 $T_j$ 读取了事务 $T_i$ 之前写入的数据项, 则 $T_i$ 的 commit 必须出现在 $T_j$ 的 commit 之前

    可恢复调度: 先写的事务先提交

    否则:

    • 若 $T_j$ 先提交
    • 随后 $T_i$ abort
    • $T_j$ 已经基于无效数据提交, 无法正确恢复

    6.2 Cascading Rollback

    cascading rollback 级联回滚:

    一个事务失败导致一系列读过它数据的事务也必须回滚

    这会撤销大量工作, 应尽量避免

    6.3 Cascadeless Schedule

    cascadeless schedule 无级联调度: 对于每一对事务 $T_1$, $T_2$:

    • 若 $T_2$ 要读取 $T_1$ 写入的数据
    • 则 $T_1$ 的 commit 必须出现在 $T_2$ 的 read 之前

    关系:

    每个 cascadeless schedule 都是 recoverable

    DBMS 通常希望限制调度为 cascadeless

    7. Implementation of Isolation

    最简单的隔离实现:

    • 一次只允许一个事务执行
    • 产生 serial schedule

    缺点:

    • 并发性极差

    为了保持一致性, schedule 应满足:

    • conflict serializable 或 view serializable
    • recoverable
    • 最好 cascadeless

    并发控制协议在两者之间权衡:

    • 允许的并发度
    • 协议自身的开销

    有些协议只允许 conflict-serializable schedule

    有些协议可以允许 view-serializable 但非 conflict-serializable schedule

    8. Testing for Serializability

    给定事务集合 $T_1, T_2, ..., T_n$ 的一个 schedule, 可以用 precedence graph 判断 conflict serializability

    8.1 Precedence Graph 优先图

    precedence graph 前驱图/优先图:

    • 有向图
    • 顶点是事务
    • 若 $T_i$ 和 $T_j$ 有冲突操作
    • 且 $T_i$ 更早访问导致冲突的数据项
    • 则画边: $$ T_i \rightarrow T_j $$

    可以在边上标记发生冲突的数据项

    8.2 Test for Conflict Serializability

    定理:

    一个 schedule 是 conflict serializable 当且仅当它的 precedence graph 无环(acyclic)

    若 precedence graph 无环:

    • 可以对图做 topological sorting 拓扑排序
    • 得到一个等价的串行化顺序

    例如可能得到: $$ T_1 \rightarrow T_3 \rightarrow T_2 \rightarrow T_4 $$

    或: $$ T_1 \rightarrow T_2 \rightarrow T_3 \rightarrow T_4 $$

    8.4 Concurrency Control vs. Serializability Tests

    执行后再检测 serializability 已经太晚

    DBMS 的目标是:

    • 设计 concurrency control protocol
    • 从一开始就保证产生的 schedule 可串行化

    serializability test 的作用:

    • 帮助理解并发控制协议为什么正确
    • 不是实际执行时的主要控制手段
