# Chapter 19: Recovery System

## 1. Failure Classification 故障分类

数据库恢复系统的目标:

> 即使发生故障, 也要保证事务的 atomicity 和 durability, 并保持数据库一致性

常见故障:

**Transaction failure 事务故障**

- logical errors
  - 溢出
  - 输入错误
  - 数据不存在
- system errors
  - DBMS 因某些错误主动终止事务
  - 例如 deadlock

**System crash 系统崩溃**

- 电源故障
- 硬件故障
- 软件故障

**fail-stop assumption 故障停止假设**

- 系统崩溃不会破坏 non-volatile storage(非易失性存储) 中的内容
- DBMS 通过完整性检查防止磁盘数据损坏

**Disk failure 磁盘故障**

- 磁头损坏等导致磁盘部分或全部内容丢失
- 假设这种破坏可以被检测到
  - 磁盘使用 checksum 检测错误

### 1.1 Recovery Algorithms

恢复算法包含两个部分:

1. 正常事务处理时采取的动作
   - 记录足够信息
   - 使故障后可以恢复
2. 故障发生后采取的动作
   - 将数据库恢复到满足 atomicity, consistency, durability 的状态

## 5. Log-Based Recovery 基于日志的恢复

**log 日志**:

> 假设直接写入 stable storage 上, 记录数据库更新活动的 log records 序列

常见 log record:

1. `<Ti start>`
   - 事务 $T_i$ 开始
2. `<Ti, X, V1, V2>`
   - $T_i$ 对数据项 $X$ 执行 write
   - $V_1$ 是 old value
   - $V_2$ 是 new value
3. `<Ti commit>`
   - $T_i$ 成功完成
4. `<Ti abort>`
   - $T_i$ abort

事务只要 `<Ti commit>` 写入 log, 就认为已提交

两种基于 log 的方法:

- deferred database modification 延迟数据库修改
- immediate database modification 立即数据库修改

---

## 6. Deferred Database Modification 延迟数据库修改

核心思想:

- 所有修改先记录到 log
- 实际数据库写入推迟到事务 partial commit 之后

假设事务串行执行

流程:

1. 事务开始时写 `<Ti start>`
2. 每个 `write(X)` 只写 log record:
$$
<T_i, X, V>
$$
其中 $V$ 是 X 的新值, 不再记录 old value
3. 此时不修改数据库
4. 事务 partial commit 时写 `<Ti commit>`
5. 读取 log, 根据 log 执行之前推迟的写操作

> 因为 commit 前数据库未被修改, 所以不需要 old value
![Pasted image 20260627175947](images/Pasted%20image%2020260627175947.png)
### 6.1 Recovery for Deferred Modification

故障恢复时:

事务 $T_i$ 需要 redo 当且仅当 log 中同时存在:

- `<Ti start>`
- `<Ti commit>`

**redo(Ti)**:

- 将 $T_i$ 更新过的所有数据项设为 log 中的新值

规则:

- 未提交事务不需要恢复
- 已提交但未真正写入磁盘的事务必须 REDO

---

## 7. Immediate Database Modification 立即数据库修改

核心思想:

- 未提交事务的更新可以在事务 commit 前写入数据库
- 因此恢复时可能需要 undo

log record 必须包含:

$$
<T_i, X, V_1, V_2>
$$

- $V_1$: old value
- $V_2$: new value

要求:

> update log record 必须在数据库 item 写入前写到 stable storage

这就是 **WAL(Write Ahead Log)** 的基础

更新 block 可以在 commit 前或 commit 后输出

block 输出顺序也可以不同于事务 write 顺序
![Pasted image 20260627181654](images/Pasted%20image%2020260627181654.png)
### 7.1 Recovery for Immediate Modification

恢复操作包括:

**undo(Ti)**

- 从 $T_i$ 的最后一条 log record 向前扫描
- 将更新过的数据恢复为 old value

**redo(Ti)**

- 从 $T_i$ 的第一条 log record 向后扫描
- 将更新过的数据设为 new value

两者都必须是 **idempotent 幂等**:

> 执行多次与执行一次效果相同

故障恢复规则:

- 若 log 中有 `<Ti start>` 但没有 `<Ti commit>`, 则 undo $T_i$
- 若 log 中同时有 `<Ti start>` 和 `<Ti commit>`, 则 redo $T_i$

若事务之前已经被 undo 并写了 `<Ti abort>`, 崩溃后恢复时仍会 redo 原历史

这称为:

> **repeating history 重复历史**

虽然看似浪费, 但可以简化恢复算法

## 8. Checkpoints 检查点

早期恢复过程的问题:

- 搜索整个 log 很耗时
- 可能重复 redo 已经写入 stable storage 的事务

定期执行 **checkpointing** 用于减少恢复工作量

**checkpoint 过程:**

1. 将内存中的所有 log records 输出到 stable storage
2. 将所有 modified buffer blocks 输出到磁盘
3. 写 log record:
$$
<checkpoint\ L>
$$
其中 $L$ 是一个`list` 是 checkpoint 时仍 active 的事务列表, 即已经`start`但是没有`commit`

> checkpoint 期间会暂停所有更新

**恢复时:**

1. 从 log 尾部向前找到最近的 `<checkpoint L>`
2. 只考虑:
   - $L$ 中的事务
   - checkpoint 后开始的事务
3. checkpoint 前已经 commit 或 abort 的事务可以忽略
4. 为 undo, 需要继续向前扫描到 $L$ 中每个事务的 `<Ti start>`
![Pasted image 20260627183310](images/Pasted%20image%2020260627183310.png)
### 8.1 Recovery Algorithm

事务正常 rollback:

1. 从 log 尾部向前扫描 $T_i$ 的 log records
2. 对 `<Ti, Xj, V1, V2>`:
   - 将 $X_j$ 恢复为 $V_1$
   - 写 compensation log record 补偿日志记录(也要遵循WAL):
$$
<T_i, X_j, V_1>
$$
3. 找到 `<Ti start>` 后停止
4. 写 `<Ti abort>`

故障恢复分两阶段:

**Redo phase**

1. 找最近 `<checkpoint L>`
2. `undo-list = L`
3. 从 checkpoint 向前扫描
4. 遇到普通 update log 或 redo-only log, 执行 redo
5. 遇到 `<Ti start>`, 将 $T_i$ 加入 undo-list
6. 遇到 `<Ti commit>` 或 `<Ti abort>`, 从 undo-list 删除 $T_i$

**Undo phase**

1. 从 log 尾部向前扫描
2. 对 undo-list 中事务的普通 update log:
   - 执行 undo
   - 写 compensation log record
3. 遇到 undo-list 中事务的 `<Ti start>`:
   - 写 `<Ti abort>`
   - 从 undo-list 删除该事务
4. undo-list 为空时停止

## 9. Buffer Management

### 9.1 Log Record Buffering

log record 通常比一个 block 小很多

因此:

- log records 会先缓存在主存中
- 满一个 log block 后再写 stable storage
- 或在 log force 时强制写出

**log force 强制日志**:

- 为提交事务, 强制将该事务的所有 log records, 包括 `<Ti commit>`, 写入 stable storage

**log buffering 必须遵守**:

1. log records 按创建顺序写入 stable storage
2. 事务只有在 `<Ti commit>` 输出到 stable storage 后才进入 commit 状态
3. `<Ti commit>` 输出前, 该事务所有 log records 必须已输出
4. 数据 block 写入数据库前, 与该 block 数据相关的所有 log records 必须已输出到 stable storage

第 4 条称为:

> **write-ahead logging rule 先写日志规则 / WAL**

### 9.2 Database Buffering

数据库维护内存 buffer 存放 data blocks

当需要新 block 且 buffer 满时:

- 选择一个 block $B_i$ 移出
- 若 $B_i$ 被修改过, 必须输出到磁盘

若 $B_i$ 中包含未提交更新, 根据 WAL:

1. 先输出与 $B_i$ 相关的 undo log records
2. 再输出 $B_i$
3. 读入新 block

为了**防止输出时 block 正在被更新**:

- 写数据项前, 事务请求该 block 的 exclusive latch
- 写完后释放 latch
- 输出 block 前, 系统也要获得 exclusive latch

**latch 闩锁**:

- 持有时间很短
- 用于保护内存数据结构或 block
- 不需要遵守事务锁协议

### 9.3 Dual Paging Problem

数据库 buffer 可实现为:

- DBMS 保留的真实主存区域
	- 缺点：预先分配，OS很难通过实际需求调整，灵活性受限
- virtual memory

virtual memory 的问题:

- OS 可能将修改过的 buffer page 写到 swap space
- DBMS 想写该 page 到数据库磁盘时, 可能需要先从 swap space 读回来
- 导致额外 I/O

这称为:

> **dual paging problem**

避免它通常需要 OS 支持

### 9.4 Fuzzy Checkpointing

普通 checkpoint 会长时间暂停更新

**fuzzy checkpointing** 允许 checkpoint 期间继续事务更新

步骤:

1. 暂停所有事务更新
2. 写 `<checkpoint L>` 并 force log 到 stable storage
3. 记录 modified buffer blocks 列表 $M$
4. 允许事务继续执行
5. 将 $M$ 中的 modified blocks 输出到磁盘
6. 输出 block 时不得被更新
7. 遵守 WAL
8. 在磁盘固定位置 `last_checkpoint` 存储 checkpoint record 指针

恢复时:

- 从 `last_checkpoint` 指向的 checkpoint record 开始扫描
- 该 checkpoint 之前的 log records 对应更新已反映到磁盘, 不需要 redo
- 若 checkpoint 未完成时系统崩溃, 也可以安全处理

## 10. Failure with Loss of Nonvolatile Storage

前面假设 nonvolatile storage 不会丢失, 但实际可能发生磁盘故障

应对方法:

- 复制 log files
- 将 log 归档到安全位置
- 定期将整个数据库 dump 到 stable storage

**archival dump 归档转储**:

1. 将内存中的所有 log records 输出到 stable storage
2. 将所有 buffer blocks 输出到磁盘
3. 将数据库文件复制到 stable storage
4. 向 log 写入 `<dump>`

一般要求:

- dump 过程中不能有 active transaction

从 disk failure 恢复:

1. 从最近的 dump 恢复数据库
2. 查阅 log
3. redo dump 后所有已经 commit 的事务

也可以支持:

- fuzzy dump
- online dump

即允许 dump 期间仍有事务活动

## 11. Recovery with Early Lock Release

某些高并发技术会提前释放锁

例如:

- B+ tree 并发控制中的插入和删除

提前释放锁后, 不能简单用 old value 进行 physical undo

原因:

- 锁释放后, 其他事务可能已经修改了同一个 B+ tree 结构

因此需要:

> **logical undo 逻辑撤销**

例:

- undo 一个 B+ tree insert
  - 执行相应 delete
- undo 一个 B+ tree delete
  - 执行相应 insert

### 11.1 Logical Undo Logging

logical undo logging:

- undo log record 中**记录要执行的 undo operation**
- 与 physical undo logging 相对

其他例子:

- undo tuple insert:
  - delete 该 tuple
- undo deposit:
  - subtract deposited amount

### 11.2 Physical Redo

即使使用 logical undo, redo 信息仍通常物理记录:

- 对每个 write 记录 new value

原因:

- logical redo 很复杂
- 恢复开始时数据库磁盘状态可能不是 operation consistent

> physical redo 与 early lock release 不冲突

### 11.3 Operation Logging

operation logging 过程:

1. 操作开始:
$$
<T_i, O_j, operation\text{-}begin>
$$
2. 操作执行中:
   - 记录普通 physical redo / physical undo log
3. 操作完成:
$$
<T_i, O_j, operation\text{-}end, U>
$$

其中 $U$ 包含 logical undo 所需信息
![Pasted image 20260627224652](images/Pasted%20image%2020260627224652.png)
若 crash/rollback 发生在 operation 完成前:

- 找不到 operation-end
- 使用 physical undo

若 crash/rollback 发生在 operation 完成后:

- 找到 operation-end
- 使用 $U$ 做 logical undo
- 忽略该操作内部 physical undo 信息

redo 仍使用 physical redo 信息

### 11.4 Rollback with Logical Undo

事务 rollback 时:

1. 向后扫描 log
2. 若遇到普通 update record:
   - 执行 physical undo
   - 写 redo-only log record
3. 若遇到:$$<T_i, O_j, operation\text{-}end, U>$$
   - 用 $U$ 执行 logical undo
   - undo 过程中产生的更新也正常记 log
   - 操作回滚结束后写:$$<T_i, O_j, operation\text{-}abort>$$
   - 跳过该 operation-begin 之前的内部 log records
   - 遇到 `<Ti start>` 后写 `<Ti abort>`

	若遇到：`redo-only record`，忽略
	若遇到：$$<T_i,O_j,operation-abort>$$
	- 跳过所有前面的$T_i$的log记录，直到找到$$<T_i,O_j,operation-begin>$$
	若遇到：$$<T_i,start>$$停止 scan

	最后向日志中添加$$<T_i,abort>$$

跳过已撤销操作的 log 很重要:

> 防止同一个 operation 被多次 rollback

## 12. ARIES

**ARIES** 是一种现代恢复算法

特点:

- 降低正常处理开销
- 加快恢复速度
- 本章前面算法可看作 ARIES 的简化版

ARIES 使用:

- LSN log sequence number：识别日志记录
- PageLSN：表示数据库页面已经应用的更新
- physiological redo
- Dirty Page Table：避免不必要的redo
- fuzzy checkpointing：记录脏页的信息

### 12.1 Physiological Redo

**physiological redo**:

- 物理定位 affected page
- page 内部的操作可以是逻辑的

优点:

- 减少日志开销

例如删除一条记录后, page 中其他记录可能移动

- physical redo 可能需要记录 page 大部分 old/new value
- physiological redo 可以只记录删除该记录的操作

要求:

- page 输出到磁盘必须是原子的
- incomplete page output 可通过 checksum 检测

### 12.2 ARIES Data Structures

**LSN(Log Sequence Number)**

- 每条 log record 的唯一编号
- 单调递增
- 常用 log file 中的 offset 表示

**PageLSN**

- 每个 page 中存储一个 PageLSN
- 表示该 page 已经反映了哪条 log record 的效果

更新 page 的过程:

1. 对 page 加 X-latch
2. 写 log record
3. 更新 page
4. 将 log record 的 LSN 写入 PageLSN
5. 解锁 page

flush page 到磁盘前:

- 先加 S-latch

PageLSN 的作用:

- recovery 时避免重复 redo
- 保证 redo idempotence(幂等性)

**Log Record**
![Pasted image 20260628112348](images/Pasted%20image%2020260628112348.png)
每条 log record 包含:

- 当前 LSN
- 同一事务上一条 log record 的 LSN, 即 PrevLSN

**CLR compensation log record**
![Pasted image 20260628112529](images/Pasted%20image%2020260628112529.png)
![Pasted image 20260628112627](images/Pasted%20image%2020260628112627.png)
- recovery 中执行 undo action 时写入
- redo-only
- 不需要再被 undo
- 包含 `UndoNextLSN`

`UndoNextLSN`:

- 指向下一条需要 undo 的更早 log record
- 用于跳过已经 undo 过的记录

**DirtyPageTable**

记录 buffer 中已被更新但可能未写回磁盘的 pages

每个 entry 包含:

- PageLSN
- RecLSN

**RecLSN**:

> 该 page 第一次变 dirty 时对应的 LSN

checkpoint 中会记录 DirtyPageTable, 用于减少 redo 工作量
![Pasted image 20260628113203](images/Pasted%20image%2020260628113203.png)
### 12.3 Checkpoint Log in ARIES

checkpoint log record 包含:

- DirtyPageTable
- active transactions list
- 每个 active transaction 的 LastLSN

ARIES checkpoint:

- 不要求 dirty pages 在 checkpoint 时写出
- dirty pages 在后台持续 flush
- checkpoint 开销很低, 因此可以频繁执行

## 13. ARIES Recovery Algorithm

ARIES recovery 有三轮:

1. Analysis pass
2. Redo pass
3. Undo pass
![Pasted image 20260628135647](images/Pasted%20image%2020260628135647.png)
### 13.1 Analysis Pass

目标:

- 判断哪些事务需要 undo
- 判断 crash 时哪些 page 是 dirty
- 确定 RedoLSN, 即 redo 从哪里开始

步骤:

1. 从最后一个完整 checkpoint log record 开始
2. 读取 checkpoint 中的 DirtyPageTable
3. 设置:
$$
RedoLSN = min(DirtyPageTable 中所有 RecLSN)
$$
若没有 dirty page, 则 RedoLSN 为 checkpoint record 的 LSN
4. 将 undo-list 设为 checkpoint 中 active transactions
5. 读取undo-list 中每个事务的最后一条日志，让事务知道从哪里开始rollback
6. 从 checkpoint 向前扫描
7. 若发现某事务 log record 但事务不在 undo-list, 加入 undo-list
8. 遇到 update log:
   - 更新 DirtyPageTable
   - 若 page 不在表中, 加入并设置 RecLSN 为该 log 的 LSN
8. 遇到 transaction end log:
   - 从 undo-list 删除事务
9. 记录每个 undo-list 事务的 last log record

结束后:

- RedoLSN 确定 redo 起点
- DirtyPageTable 用于减少 redo
- undo-list 中事务需要 rollback

### 13.2 Redo Pass

目标:

> repeating history, 重做所有 crash 前已经发生但可能未写入磁盘的操作

从 RedoLSN 向前扫描 log

遇到 update log record:

1. 若 page 不在 DirtyPageTable, 跳过
2. 若 log record 的 LSN 小于该 page 的 RecLSN, 跳过
3. 否则从磁盘取 page
4. 若 page 的 PageLSN 小于 log record LSN, redo
5. 否则跳过

第一、二步可以避免不必要地读取 page

### 13.3 Undo Pass

目标:

> 回滚所有 incomplete transactions

优化方式:

- 对每个 undo-list 中事务, 设置 next LSN 为 analysis pass 得到的 LastLSN
- 每次选择最大的 next LSN 进行 undo
- 直接跳到该 log record, 跳过无关 log

undo 一条普通 update log:

- 执行 undo
- 生成 CLR
- CLR 的 `UndoNextLSN` 设置为该 update log 的 PrevLSN

undo 一条 CLR:

- 下一条要 undo 的 LSN 设为 CLR 的 `UndoNextLSN`

所有中间已经 undo 过的 log records 都可以跳过

`ARIES`支持部分撤销

![Pasted image 20260628143103](images/Pasted%20image%2020260628143103.png)
### 13.4 Other ARIES Features

**Nested top actions 嵌套的顶层操作**

有些操作即使事务 rollback 也不应 undo

例如:

- 为关系分配一个 page
- 即使事务回滚, 该 page 可能已经被其他事务使用

实现:

- 创建 dummy CLR
- 设置 UndoNextLSN 使 rollback 跳过该操作的 log records

**Recovery Independence**

- page 可以独立恢复
- 某些 disk pages 损坏时, 可从 backup 恢复这些 pages
- 其他 pages 仍可继续使用

**Savepoints 保存点**

- 事务可以设置 savepoint
- 可 rollback 到某个 savepoint
- 对复杂事务和死锁部分回滚有用

**Fine-grained locking**

- 索引并发算法可使用 tuple-level locking
- 需要 logical undo

**Recovery optimizations**

- DirtyPageTable 可用于 redo 阶段预取 page
- out-of-order redo:
  - 某 page 正在从磁盘读取时, 可先处理其他 log records
  - page 到达后再 redo
