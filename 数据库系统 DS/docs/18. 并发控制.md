### 1. Lock-Based Protocols

并发控制的基础是:

> 产生 serializable schedule

**lock 锁**:

> 控制多个事务并发访问同一数据项的机制

数据项可以用两种模式加锁:

1. **exclusive mode 排它锁 / X-lock**
   - 数据项既可以读, 也可以写
   - 使用 `lock-X` 请求
2. **shared mode 共享锁 / S-lock**
   - 数据项只能读
   - 使用 `lock-S` 请求

锁请求发送给 concurrency-control manager

> 事务只有在锁请求被授予后才能继续执行

#### 1.1 Lock Compatibility

锁兼容性矩阵:

| 已有锁 | 请求 S-lock | 请求 X-lock |
|---|---|---|
| S-lock | compatible | incompatible |
| X-lock | incompatible | incompatible |

结论:

- 任意多个事务可以同时持有同一数据项的 S-lock
- 若某事务持有 X-lock, 其他事务不能持有任何锁
- 若锁请求不相容, 请求事务必须等待

#### 1.2 Locking Protocol

**locking protocol 加锁协议**:

> 所有事务在请求和释放锁时必须遵守的一组规则

加锁协议限制可能产生的 schedule, 以保证并发执行正确

若协议设计不好, 可能出现:

- deadlock 死锁
- starvation 饿死: 例如一个事务想要请求对一个数据的X锁, 但是不断有事务在申请S锁, 使得其始终无法获得需要的资源
- inconsistent read

### 2. Two-Phase Locking Protocol 两段锁协议

**2PL** 将事务的加锁过程分为两个阶段:

**Phase 1: Growing Phase 增长阶段**

- 可以获得锁
- 不可以释放锁

**Phase 2: Shrinking Phase 收缩阶段**

- 可以释放锁
- 不可以再获得新锁

**lock point 锁点**:

> 事务获得最后一个锁的时刻

2PL 的性质:

> 若一个 schedule 遵守 2PL, 则该 schedule 一定 conflict serializable

并且事务可以按 lock point 的顺序串行化

**证明思路**: 证明符合2PL的调度一定是冲突可串行化的

1. 反证法:

- 若 precedence graph 中有边 $T_i \rightarrow T_j$, 则 $T_i$ 的 lock point 必须早于 $T_j$
- 若图中存在环:
$$
T_0 \rightarrow T_1 \rightarrow ... \rightarrow T_{n-1} \rightarrow T_0
$$
则会推出:
$$
\alpha_0 < \alpha_1 < ... < \alpha_{n-1} < \alpha_0
$$
矛盾

因此 precedence graph 无环

2. 对于符合2PL的调度, 假设$T_i$ 是第一个到达 lock point 的, 则可以将其所有的读写操作前移到调度的开头, 且没有通过任何冲突的操作, 这样递归下来便可以产生一个串行调度
#### 2.1 2PL 的问题

2PL 可以保证 conflict serializability, 但:

- 不能保证不会死锁
- 可能产生 cascading rollback

#### 2.2 Strict Two-Phase Locking

**strict 2PL 严格两段锁**:

- 事务必须持有所有 X-lock 直到 commit 或 abort

作用:

- 避免其他事务读取未提交写入
- 使回滚更加安全
- 可以避免级联回滚

#### 2.3 Rigorous Two-Phase Locking

**rigorous 2PL 强两段锁**:

- 事务持有所有锁, 包括 S-lock 和 X-lock, 直到 commit 或 abort

性质:

- 事务可以按 commit 顺序串行化

> 更严格的协议通常以降低并发度为代价

> 2PL 得到的一定是冲突可串行化的, 但是得到冲突可串行化的不一定要2PL
#### 2.4 Lock Conversions 锁转换

为了提高并发性, 2PL 可以允许锁转换

第一阶段:

- 可以获得 S-lock
- 可以获得 X-lock
- 可以将 S-lock 升级为 X-lock

第二阶段:

- 可以释放 S-lock
- 可以释放 X-lock
- 可以将 X-lock 降级为 S-lock

> 仍然可以保证 serializability

#### 2.5 Automatic Acquisition of Locks

事务可以只发出普通 `read(D)` / `write(D)`, 不显式写锁指令

DBMS 自动处理:

`read(D)`:

- 若事务已有 D 上的锁, 直接读
- 否则等待直到没有事务持有 D 的 X-lock
- 授予 S-lock
- 执行读

`write(D)`:

- 若已有 X-lock, 直接写
- 若已有 S-lock, 等待后升级为 X-lock
- 若没有锁, 等待直到其他事务无锁, 再授予 X-lock
- 执行写

所有锁在 commit 或 abort 后释放

### 3. Implementation of Locking

lock manager 通常作为独立模块/进程实现

事务向 lock manager 发送:

- lock request
- unlock request

lock manager 回复:

- lock grant message
- 或要求事务 rollback 的消息(检测到了死锁)

lock manager 维护:

> **lock table 锁表**
![[Pasted image 20260626203604.png]]
lock table 通常是内存中的 hash table, 以数据项名为 key

每个数据项的队列中记录:

- 已授予的锁
- 正在等待的请求
- 锁模式

处理规则:

- 新请求加入队尾
- 若与已有已授予锁相容, 则授予
- unlock 后删除请求, 并检查后续等待请求是否可授予
- 若事务 abort, 删除该事务的所有等待锁和已授予锁

### 4. Graph-Based Protocols 基于图的加锁协议

graph-based protocol 是 2PL 的替代方案

基本思想:

- 在所有数据项集合 $D=\{d_1,d_2,...,d_h\}$ 上定义偏序 $\rightarrow$
- 若 $d_i \rightarrow d_j$, 则任何同时访问 $d_i$ 和 $d_j$ 的事务必须先访问 $d_i$
- 数据项可看作一个 **directed acyclic graph**, 也称为 database graph

#### 4.1 Tree Protocol 树形协议

tree protocol 是一种简单的 graph protocol
![[Pasted image 20260627100147.png]]
![[Pasted image 20260627100411.png]]
规则:

1. 只允许 X-lock
2. 事务第一次加锁可以锁任意数据项
3. 此后事务只能在当前持有 parent 锁时, 才能锁 child
4. 数据项可以任意时间解锁
5. 同一事务释放某数据项后, 不能再次锁该数据项

优点:

- 保证 conflict serializability
- 保证 deadlock-free
- 可比 2PL 更早释放锁
- 等待时间可能更短, 并发性更高

缺点:

- 事务可能必须锁它不访问的数据项
- 增加锁开销和等待时间
- 可能降低并发性

> tree protocol 可产生某些 2PL 不能产生的 schedule, 反之亦然

### 7. Multiple Granularity 多粒度

> 例如 `SELECT * FROM ACCOUNT;` 需要对所有数据项进行加锁, 可能产生很大的开销

为了方便, DBMS 允许以不同大小的数据项加锁

例如:

- database
- area
- file / table
- record / tuple

这些粒度形成层次树 (注意区分于加锁的树形协议)
![[Pasted image 20260627101551.png]]
若事务显式锁住某个节点, 则隐式锁住该节点所有 descendants

粒度选择:

- fine granularity 细粒度: 树结构较低位置
  - 并发度高
  - 加锁开销高
- coarse granularity 粗粒度: 树结构较高位置
  - 加锁开销低
  - 并发度低

#### 7.1 Intention Locks 意向锁

问题:

- 若一个事务锁了某个 tuple
- 另一个事务想锁整张表
- 如果没有额外信息, 需要搜索整棵树检查所有 descendants

**intention lock**:

> 在显式锁某个节点前, 先在它的所有 ancestors 上加意向锁

作用:

- 让高层节点能快速判断其子树中是否已有锁
- 不需要检查所有 descendants

#### 7.2 Intention Lock Modes

三种意向锁:

**IS intention-shared 共享型意向锁**

- 表示后代节点上将有 S-lock

**IX intention-exclusive 排它型意向锁**

- 表示后代节点上将有 X-lock

**SIX shared and intention-exclusive 共享排它型意向锁**

- 当前节点以 S-mode 显式锁定
- 同时后代节点上可能有 X-lock

可以理解为:
$$
SIX = S + IX
$$

#### 7.3 Multiple Granularity Locking Scheme

事务 $T_i$ 加锁节点 $Q$ 时必须遵守:
![[Pasted image 20260627102736.png]]
1. 锁相容矩阵必须满足
2. 必须先锁 root, root 可用任意模式
3. 若要对 $Q$ 加 S 或 IS, 其 parent 必须已被 $T_i$ 以 IX 或 IS 锁住
4. 若要对 $Q$ 加 X, SIX 或 IX, 其 parent 必须已被 $T_i$ 以 IX 或 SIX 锁住
5. 事务释放过任何锁后, 不能再获得新锁
6. 事务只能在 $Q$ 的 children 都没有被自己锁住时释放 $Q$

即:

- 加锁自顶向下
- 解锁自底向上
- 同时遵守 2PL

优点:

- 增强并发性
- 降低加锁开销

### 9. Deadlock Handling 死锁处理

系统处于 deadlock 当且仅当:

> 存在一组事务, 其中每个事务都在等待该组中另一个事务

处理方式:

- deadlock prevention
- deadlock detection and recovery

#### 9.1 Deadlock Prevention

预防策略保证系统永远不会进入死锁状态

**1. Predeclaration / Conservative 2PL**

- 事务开始前一次性锁定所有需要的数据项
- 要么全部获得, 要么一个都不获得

缺点:

- 并发度低
- 很难提前知道所有需要访问的数据项

**2. Partial ordering**

- 对所有数据项定义偏序
- 事务只能按该顺序加锁
- 因而不可能形成环

**3. Wait-die scheme**

- 非抢占式
- 老事务可以等待年轻事务
- 年轻事务不能等待老事务, 会被 rollback

**4. Wound-wait scheme**

- 抢占式
- 老事务 rollback
- 年轻事务等待老事务

> rollback 的事务重启时保留原 timestamp, 可以避免 starvation
![[Pasted image 20260627104338.png]]
**5. Timeout-Based Scheme**

- 事务等待锁超过指定时间后自动 rollback

优点:

- 简单
- 不会死锁

缺点:

- 可能 starvation
- timeout 时间难以设定

#### 9.2 Deadlock Detection

使用 **wait-for graph 等待图**

图 $G=(V,E)$:

- $V$: 系统中所有事务
- $E$: 等待关系

若 $T_i$ 等待 $T_j$ 释放某数据项, 则有边:
$$
T_i \rightarrow T_j
$$

规则:

- 当 $T_i$ 请求的数据项被 $T_j$ 持有时, 插入边
- 当 $T_j$ 不再持有 $T_i$ 需要的数据项时, 删除边

**判断:**

> wait-for graph 有环当且仅当系统死锁

系统需要周期性运行 deadlock detection algorithm 检测环
![[Pasted image 20260627105044.png]]
#### 9.3 Deadlock Recovery

检测到死锁后:

1. 选择某个事务作为 victim
2. rollback victim 以打破死锁

victim 选择:

- 选择 rollback 代价最小的事务

rollback 范围:

- total rollback
  - 回滚整个事务并重启
- partial rollback
  - 只回滚到足以打破死锁的位置

避免 starvation:

- 将事务被 rollback 的次数加入 victim 选择代价

### 10. Insert, Delete, and Predicate Reads

在 2PL 下:

- delete tuple 前必须持有该 tuple 的 X-lock
- insert 新 tuple 后事务获得该 tuple 的 X-lock

问题:

> insertion 和 update 可能导致 phantom phenomenon **幻影现象**

例如:

- 事务 $T_1$ 扫描关系中满足某谓词的 tuple
- 事务 $T_2$ 插入一个满足该谓词的新 tuple
- 二者可能没有访问任何相同 tuple
- 但逻辑上发生冲突

若只使用 tuple locks, 可能得到 non-serializable schedule

#### 10.1 Relation-Level Predicate Information Lock

一种简单方案:

- 为关系设置一个代表“关系包含哪些 tuple”的数据项
- 扫描关系的事务对该数据项加 S-lock
- 插入或删除 tuple 的事务对该数据项加 X-lock

缺点:

- 并发度非常低
- 两个插入不同 tuple 的事务也会互相阻塞

#### 10.2 Index Locking Protocol

更好的方案是使用 index locking

规则:

1. 每个关系至少有一个索引
2. 对关系的访问必须通过某个索引
3. lookup 时, 事务必须对访问到的 index leaf nodes 加 S-lock
4. insert/delete/update tuple 时, 必须更新该关系所有索引
5. 对每个受影响的 index leaf node 加 X-lock
6. 遵守 2PL

> index locking 能以更高并发度防止 phantom phenomenon

### 11. Weak Levels of Consistency

某些系统允许低于 serializable 的一致性级别

#### 11.1 Degree-Two Consistency

与 2PL 的区别:

- S-lock 可以随时释放
- 锁可以随时获得
- X-lock 必须持有到事务结束

特点:

- 不保证 serializability
- 需要程序员保证不会产生错误状态

#### 11.2 Cursor Stability

cursor stability 是 degree-two consistency 的特例:

- 读取时, 每个 tuple 被锁定
- 读完立即释放锁
- X-lock 持有到事务结束

#### 11.3 SQL Isolation Levels

SQL 允许 non-serializable executions

**Serializable**

- 默认最高级别
- 保证 serializable

**Repeatable Read**

- 只能读取已提交记录
- 重复读取同一记录应返回相同值
- 但不能防止 phantom phenomenon

**Read Committed**

- 类似 degree-two consistency
- 多数系统按 cursor stability 实现

**Read Uncommitted**

- 允许读取未提交数据
